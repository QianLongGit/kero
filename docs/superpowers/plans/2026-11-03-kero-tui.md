# `kero tui` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A full-screen `kero tui` picker that lists live sessions and panes, attaches on selection (keyboard, mouse, touch), and offers n/s/d/r/filter management actions — zero new dependencies.

**Architecture:** Hand-written ANSI TUI in three layers under `internal/cli/`: pure view functions (state → rows/footer), a pure input parser (bytes → key/mouse events, SGR 1006), and a pure state machine (events → model mutation + pending action); `tuiCmd` wires them into a raw-mode render loop over the existing `watch` event stream, then hands off to the existing `attachLoop` for the selected pane.

**Tech Stack:** Go stdlib + already-present deps only (`golang.org/x/term`); reuse `internal/client`, `internal/proto`, existing CLI helpers (`connect`, `parse`, `lastActive`, `focusPane`, `attachLoop`, `termPixels`, `winchSignals`).

**Spec:** `docs/superpowers/specs/2026-11-03-kero-tui-design.md` (approved; executor reads both).

## Global Constraints

- Zero new dependencies — `go.mod`/`go.sum` must not change.
- No daemon or protocol changes; `proto.Version` untouched. All RPCs reuse existing methods: `create` / `split` (both `proto.CreateParams`), `pane.close` (`proto.IDParams`), `close` (`proto.CloseParams`), `rename` (`proto.RenameParams`), `watch`, `state`.
- Comments are English prose explaining why (repo convention); no ASCII-art block headers, match `attach.go`'s tone.
- One feature per file: new files are `tui_view.go`, `tui_input.go`, `tui.go` (+ `*_test.go` each). Existing files touched: `internal/cli/cli.go` (one case + usage lines), `docs/cli.md` (one entry).
- **No `git commit` steps** — user rule: no commits unless asked. Each task ends at "tests pass + `go vet` clean".
- Terminal conventions: raw mode via `term.MakeRaw/Restore` on `os.Stdin.Fd()`; alt-screen `\x1b[?1049h/l`; mouse `\x1b[?1002h/l` + `\x1b[?1006h/l`; cursor hide `\x1b[?25l/h`. Colors: terminal default 16 colors only, no RGB.
- Tests follow `internal/cli` style (see `attach_test.go`); isolate env with `t.Setenv("KERO_HOME", t.TempDir())` where a test touches settings/daemon paths (none should — all new tests are pure-function tests).

## Review Focus

Inputs the spec implies but no happy path exercises; each pinned by a test in the owning task:

1. **Empty state** — `st.Sessions` empty must render a "no sessions" hint row and `n` must still open the new-session prompt, not crash or select row -1 → Task 1 (rows) + Task 3 (step).
2. **Escape sequence split across reads** — `\x1b` at the end of one `feed` batch, `[<0;5;2M` in the next, must decode to one click at (5,2), not garbage keys → Task 2.
3. **UTF-8 rune split across reads** — a Chinese title filter typed as 3-byte runes torn between batches must round-trip; filter matching is case-insensitive but rune-exact → Task 2 (parser) + Task 1 (match).
4. **Narrow terminal** — at width 15 the row must truncate (no wrap, no overflow past the last column), footer still visible → Task 4 (frame).
5. **Exited session rows** — `Status == proto.Exited` sessions still list (grey dot) and Enter still resolves a pane; the attach path's failure is the normal CLI one (`errNotFound`), never a TUI panic → Task 1 (dot) + Task 3 (attach on exited row returns the pane, no special-casing).
6. **List taller than the screen** — 10 sessions + panes on a 24-line phone screen must scroll: a sliding viewport follows the cursor, clicks map screen rows through the viewport, and no row ever renders outside the frame → Task 3 (viewport in the model) + Task 4 (viewport render + click mapping).

### Task 2: Input parser — keys, SGR mouse, line editor

**Files:**
- Create: `internal/cli/tui_input.go`
- Test: `internal/cli/tui_input_test.go`

**Interfaces:**
- Consumes: nothing from Task 1.
- Produces:
  - `type tuiKey struct { Rune rune; Digit int; Name string }` — `Rune` is a printable rune else 0; `Digit` is 1-9 for '1'-'9' else 0; `Name` ∈ `{"up","down","left","right","enter","escape","backspace","tab","ctrl+w","ctrl+u",""}`.
  - `type tuiMouse struct { Col, Row, Wheel int }` — 1-based; `Wheel` -1 up / +1 down / 0 click.
  - `type tuiEvent struct { Key tuiKey; Mouse tuiMouse; IsMouse bool }`
  - `type inputParser struct{ … }` with `func (p *inputParser) feed(b []byte) []tuiEvent` — buffers incomplete sequences across calls (fields unexported; a plain `[]byte` pending buffer + index suffice). CSI sequences: arrows (`\x1b[A/B/C/D`), SGR mouse `\x1b[<b;c;r(M|m` — click when `b == 0` press (`M` suffix); wheel when `b == 64` (up, `Wheel -1`) or `b == 65` (down, `Wheel +1`). Lone `\x1b` with nothing following in the batch is buffered, not emitted. C0 controls: 0x0d/0x0a→enter, 0x1b→escape (when standalone), 0x7f→backspace, 0x09→tab, 0x17→ctrl+w, 0x15→ctrl+u, '1'-'9'→Digit, other printable→Rune. Unknown CSI: swallow whole.
  - `type lineEditor struct { buf []rune; pos int }` (exported fields — Task 3 reads `buf`/`pos` for cursor rendering) with `func (e *lineEditor) key(k tuiKey) bool` (apply one editing key: printable inserts at `pos`, backspace/left/right move/delete, ctrl+w deletes the word left, ctrl+u clears; returns false for non-editing keys, leaving state untouched) and `func (e *lineEditor) text() string`.

- [ ] **Step 1: Write failing tests** — table tests feeding byte slices: (a) `q` alone → Rune 'q'; (b) `\x1b[B` → Name "down"; (c) SGR click `\x1b[<0;5;2M` → Mouse{5,2,0}; (d) wheel `\x1b[<64;1;1M` → Wheel -1, `\x1b[<65;1;1M` → +1; (e) torn sequence: `feed("\x1b")` returns nothing, `feed("[<0;7;3M")` returns the click at (7,3); (f) torn UTF-8: `feed("\xe4\xbd")` then `feed("\xa0")` → one Rune '你'; (g) `3` → Digit 3; (h) enter/escape/backspace/ctrl+w/ctrl+u names; (i) unknown CSI `\x1b[200~` swallowed, and a following `x` still parses as Rune; (j) editor: type "ab", ←, "X" → text "aXb"; ctrl+w on "foo bar" → "foo "; ctrl+u → "".

### Task 3: State machine — events to actions, action×row matrix

**Files:**
- Create: `internal/cli/tui.go` (only the model + step function + `tuiMode` moved here if you prefer — keep `tuiMode` wherever Task 1 put it; do not duplicate)
- Test: `internal/cli/tui_test.go`

**Interfaces:**
- Consumes: `tuiRow`, `tuiRows`, `rowMatches` (Task 1); `tuiKey/tuiMouse/tuiEvent/lineEditor` (Task 2); `proto.State`, `focusPane(s proto.Session) (string, error)` (attach.go:124).
- Produces:
  - `type tuiAction uint8` with `tuiNone/tuiAttach/tuiNew/tuiSplit/tuiClose/tuiRename/tuiQuit`.
  - `type tuiPending struct { Kind tuiAction; Pane string; Text string; SessionID string }` — `Pane` resolved for attach (`focusPane` on session rows) and for split's target pane; `Text` carries the prompt result for new/rename; `SessionID`+`Pane` identify close's target (session-level when `Pane == ""` on a session row).
  - `type tuiModel struct { Mode tuiMode; Cursor int; Offset int; Filter string; Editor lineEditor; Action tuiAction; Target tuiRow; Live bool }` — `Offset` is the sliding viewport's first visible row index.
  - `func tuiStep(m tuiModel, ev tuiEvent, st proto.State, height int) (tuiModel, *tuiPending, error)` — value semantics; returns updated model, a pending action (nil unless one fires), error only when an attach target resolution fails (`errNotFound` wrapped). `height` is the count of visible list rows (screen lines minus header minus the two bottom lines); after any cursor change or list change, clamp `Offset` so `Cursor` stays inside `[Offset, Offset+height)` when the list is that long. Mouse clicks arrive as screen rows (1-based, as SGR sends them): map `list row = ev.Mouse.Row - 1 + m.Offset` (the header is exactly one line — a layout contract with `drawTUI`); wheel moves the cursor one row, not the viewport directly.
  - Row list is not a parameter: `tuiStep` derives it via `tuiRows(st)` + `m.Filter` so the model and the visible list can never diverge. Cursor clamping: after filter/state changes keep cursor in range, preferring to hold the same session.

  Behavior (from the spec, verbatim rules):
  - list mode: up/down move (wrap), Digit 1-9 jumps cursor to visible row N (no enter needed to move), enter → `tuiAttach` (session row resolves `focusPane`, pane row its ID), `n/s/d/r` → enter prompt/confirm modes with `m.Target = visible row at cursor` (`s`'s target pane = pane row's ID or session row's `FocusPane` ID; `r` always session-level: `SessionID` set, `Pane == ""`), `/` → filter mode (editor seeded with current `Filter`), `q` → `tuiQuit`, mouse click → cursor to that row then `tuiAttach`, wheel → cursor move, `esc`: with an active filter clears it, without one quits (the spec's `q`·`esc` pair).
  - filter mode: only editing keys + enter (return to list, cursor to first match) + escape (clear filter, back to list). Any of `n/s/d/r/q` keystrokes land in the editor as text, not actions.
  - prompt mode (new: empty editor; rename: seeded with target session's `Name`): editing keys + enter → `tuiPending` with `Text` + back to list + escape cancels.
  - confirm mode (close): `y` fires `tuiClose` (session-level for session rows: `Pane == ""`, `SessionID` set; pane-level for pane rows: `Pane` set), any other key but escape is ignored, escape cancels.
  - Empty visible list: only `n`, `/`, `q` act; enter/arrows no-op (no panic).

- [ ] **Step 2: Run** `go test ./internal/cli/ -run TestTUIStep -v` — expect compile failure.
